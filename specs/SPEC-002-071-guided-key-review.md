## Problem

Owner (2026-10-24, viewer 3.3.6): "'2. Review a participant key' flow has friction; it's not clear
that I have to copy. 'Paste the fingerprint you independently confirmed' gives a hint but as a user
I do not know that I need to check that. I like the idea that I need to paste it, not that I just
have a button. Maybe a CTA to 'copy the fingerprint' and a CTA 'paste the fingerprint'; still
manual but the UI/UX gives hints what to do; update manuals, we need well illustrated
documentation / user guides with diagrams and screenshots from the board."

Today (scripts/signing-ui.js, review section) the task shows one paragraph about a separate
channel, the board-listed fingerprint in a `<code>`, one input "Paste the fingerprint you
independently confirmed" and the approve button. It does not say where the confirmed fingerprint
comes from, what to send to the other person, or how the key owner finds their own fingerprint.

## Design

Approval stays a deliberate manual paste. No one-click approve. The UI guides the steps.

### A. Review task as numbered steps (`#signingReviewSteps`)
After the participant select and the key card:

1. **Get their fingerprint from them.** "Ask NAME to send you their fingerprint through a channel
   you already trust: in person, a phone call, or a chat app you already use with them. Not this
   board." Under it, a one-line "How NAME finds it" disclosure with both ways:
   - viewer: **Tools → Signing → Sign as me → Copy my fingerprint** (item B);
   - CLI: the exact `boardctl` command that prints a participant's own key fingerprint from the
     key file (use an existing canonical command; if none prints it from the private key file,
     document `boardctl signing inspect` and file a canonical follow-up instead of inventing one).
   Plus **Copy what to send them** (`#signingCopyRequest`): copies a short request text naming the
   board, the participant and the board-listed fingerprint prefix + last 8 characters only, so
   the other person can confirm without the full value being simply echoed back.
2. **Paste what they sent you.** The existing `#signingFingerprint` input (same ID), relabelled
   "Fingerprint NAME sent you", with a **Paste** button (`#signingPaste`, Clipboard API
   `readText`; if not permitted, a hint "Press Cmd+V / Ctrl+V in the field"). Whitespace and line
   breaks are stripped on paste.
3. **Compare.** Live result under the input, updated on every change:
   - match: "✓ Matches the key on this board" (success tone);
   - mismatch: "✗ Does not match", with the first differing position highlighted in both values
     (board value and pasted value shown in groups of 4 characters);
   - partial/empty: neutral "Paste the full fingerprint, including the prefix".
4. **Approve.** The existing approve button, enabled only on a match. Its label becomes
   "Approve NAME's key".

**Echo guard.** The board-listed fingerprint is not offered as a copy button in the review task.
If the pasted value equals what this dialog put on the clipboard (via `#signingCopyRequest`) or
the user copies the `<code>` text and pastes it within the same dialog session, show a warning
"This is the value shown on this board. Paste the one NAME sent you from their own device." and
require ticking "I confirmed it with NAME outside this board" before Approve enables. Detection
uses the dialog's own copy events only; no clipboard reading without the user's Paste action.

### B. Key owner's own fingerprint (`#signingMyFingerprint`)
In **Sign as me**, once the persona's key file is unlocked: "Your key fingerprint" with the value
in groups of 4 and **Copy my fingerprint**. The value is derived from the unlocked key file, not
from the board (that is the point: it comes from the owner's device).

### C. Own key shortcut
When the participant under review is the current persona and its key file is unlocked in this
browser, step 1-3 can be satisfied by **Check with my key file** (`#signingCheckOwnKey`): it
compares the unlocked key's fingerprint with the board-listed one and fills the comparison result;
the user still clicks Approve. If not unlocked, the button unlocks first (existing flow). Text
explains: "Your key file is on this device, so it can confirm the board lists your key."

### D. Illustrated guides
- `docs/guides/signing.md`: rewrite "Approving a participant key" as an illustrated walkthrough:
  one screenshot per step (1-4), the own-key shortcut, and the "what to send them" text; plus
  an SVG diagram of the two channels (board vs trusted channel) generated by the existing
  `scripts/build_signing_diagrams.js` pipeline (add a diagram, keep `--check` passing).
- Screenshots are produced by a script (extend `scripts/screenshot_signing.js` or add one) from
  deterministic fixtures, written to `docs/images/`, and wired into `npm run screenshots:all`.
- A test asserts every image referenced by docs/guides/*.md and README.md exists and every new
  screenshot name the script declares is referenced by a guide.

## Acceptance criteria

- [x] AC1: the review task shows steps 1-4 with the texts above (English and Polish); the "How NAME
  finds it" disclosure names the viewer path and a CLI command that exists in the pinned canonical
  `boardctl` (test parses `vendor/agent-file-board` help or source to confirm the command exists).
- [x] AC2: `#signingCopyRequest` puts the request text on the clipboard (Playwright clipboard
  permissions); it contains the board name/ID, the participant and the shortened fingerprint, and
  not the full fingerprint.
- [x] AC3: `#signingPaste` fills the field from the clipboard and strips whitespace; with clipboard
  read denied it shows the keyboard hint and no page error.
- [x] AC4: comparison states: exact match -> success and Approve enabled with "Approve NAME's key";
  one character changed -> mismatch with the differing group highlighted and Approve disabled;
  truncated -> neutral and disabled.
- [x] AC5: echo guard: copying the board value from the key card and pasting it shows the warning
  and keeps Approve disabled until the confirmation box is ticked; a value pasted that did not
  originate in the dialog shows no warning.
- [x] AC6: `#signingMyFingerprint` appears after unlocking in Sign as me, equals the fingerprint
  derived from the key file, and copies it.
- [x] AC7: own-key shortcut: reviewing the current persona with its key unlocked, "Check with my
  key file" yields a match; with a key file for a different key it yields a mismatch and Approve
  stays disabled.
- [x] AC8: the full existing approval behaviour is unchanged after Approve (pins, counts from
  SPEC-002-069, composer status); existing signing tests pass unchanged except where this spec
  changes a label (rewritten, not loosened).
- [x] AC9: non-vacuity: an in-test mutation that makes the comparison always report a match fails
  AC4; one that skips the echo-guard check fails AC5.
- [x] AC10: docs per D, screenshots generated by the script, image-reference test passes;
  layout snapshots for the `signing-review` scene updated (tests/visual, if merged) and the
  scene list gains `signing-review-match` and `signing-review-mismatch`.
  (Layout snapshots updated and both scenes added after rebasing onto SPEC-002-070. Linux pixel
  baselines for signing-review and the two new scenes come from the update_visual_baselines CI run.)
- [x] AC11: released as viewer 3.3.7; CHANGELOG.

Out of scope: any automatic approval, QR codes, any network channel. No VoiceOver/screen-reader
checks (owner policy).
